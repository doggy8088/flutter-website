本地快取

  1. 開始使用 chevron_right
  2. 基礎知識 chevron_right
  3. 本地快取

現在你已經學會如何透過網路從伺服器載入資料，你的 Flutter 應用程式應該感覺更加生動了。然而，僅僅因為你可以從遠端伺服器載入資料，並不代表你總是應該這麼做。有時候，重新渲染上一次網路請求取得的資料，比起重複發送請求並讓使用者再次等待完成，會是更好的選擇。這種將應用程式資料保留起來，以便未來再次顯示的技術稱為快取（caching），本頁將介紹如何在你的 Flutter 應用程式中實現這項任務。

快取簡介

#

最基本來說，所有快取策略都可歸結為相同的三步驟操作，以下以偽程式碼表示：

dart
Data? _cachedData;

Future<Data> get data async {
    // Step 1: Check whether your cache already contains the desired data
    if (_cachedData == null) {
        // Step 2: Load the data if the cache was empty
        _cachedData = await _readData();
    }
    // Step 3: Return the value in the cache
    return _cachedData!;
}

這個策略有許多有趣的變化方式，包括快取的位置、你主動將資料寫入（或稱「預熱」）快取的程度，以及其他方式。

常見快取術語

#

快取（Caching）有其專屬術語，以下對部分術語進行定義與說明。

Cache hit（快取命中）
當應用程式在快取中已經包含所需資訊，無需從真正的資料來源載入時，就稱為「快取命中」。
Cache miss（快取未命中）
當應用程式的快取為空，必須從真正的資料來源載入所需資料，並將其儲存到快取中以供未來讀取時，就稱為「快取未命中」。

快取資料的風險

#

當資料的來源（source of truth）已經變更，而快取中的資料尚未更新時，應用程式就會出現過時快取（stale cache），這會導致應用程式有顯示舊資料的風險。

所有快取策略都可能導致保留過時資料。不幸的是，驗證快取是否為最新的動作，通常所需時間與完整載入資料相當。這意味著，大多數應用程式只有在信任資料於執行時是最新的（無需驗證）時，才會從快取中獲得效益。

為了應對這個問題，大多數快取系統都會對每一筆快取資料設定時效限制。當超過這個時限後，原本可能的快取命中會被視為快取未命中，直到載入新鮮資料為止。

在電腦科學領域有個著名的笑話：「電腦科學中最難的兩件事是快取失效、命名，以及 off-by-one 錯誤。」😄

儘管有這些風險，全球幾乎每個應用程式都大量使用資料快取。接下來本頁會探討多種在你的 Flutter 應用程式中快取資料的方法，但請注意，這些方法都可以根據你的需求進行調整或組合。

在本機記憶體中快取資料

#

最簡單且效能最佳的快取策略是記憶體內快取（in-memory cache）。這種策略的缺點是，因為快取只存在於系統記憶體中，當前工作階段結束後，資料就不會被保留。（當然，這個「缺點」同時也有自動解決大多數過時快取問題的優點！）

由於其簡單性，記憶體內快取的實作與上方的偽程式碼非常相似。不過，建議你採用經過驗證的設計原則，例如repository pattern，來組織你的程式碼，避免像上述的快取檢查邏輯散布在整個程式碼庫中。

想像有一個UserRepository類別，同時負責將使用者資料快取於記憶體中，以避免重複的網路請求。其實作可能如下所示：

dart
class UserRepository {
  UserRepository(this.api);
  
  final Api api;
  final Map<int, User?> _userCache = {};

  Future<User?> loadUser(int id) async {
    if (!_userCache.containsKey(id)) {
      final response = await api.get(id);
      if (response.statusCode == 200) {
        _userCache[id] = User.fromJson(response.body);
      } else {
        _userCache[id] = null;
      }
    }
    return _userCache[id];
  }
}

這個 UserRepository 遵循多項經過驗證的設計原則，包括：

  • 依賴注入（dependency injection），有助於測試
  • 低耦合（loose coupling），可保護周邊程式碼不受其實作細節影響，以及
  • 關注點分離（separation of concerns），可避免其實作同時處理過多責任。

最棒的是，無論在單一使用者會話期間，使用者在你的 Flutter 應用程式中造訪多少次載入某個使用者資料的頁面，UserRepository 類別都只會透過網路載入該資料 一次。

然而，使用者可能會對每次重新啟動應用程式時都要等待資料載入感到厭煩。針對這種情況，你應該選擇下方介紹的其中一種持久化快取策略。

持久化快取

#

將資料快取於記憶體中，無法讓你的寶貴快取超越單一使用者會話的壽命。 若想在應用程式每次全新啟動時也能享有快取命中的效能優勢，你需要將資料快取於裝置的硬碟上。

使用 shared_preferences 快取資料

#

shared_preferences 是一個 Flutter 套件，能夠在 Flutter 支援的六大平台上，包裝各自平台的 鍵值儲存（key-value storage）。 雖然這些底層平台的鍵值儲存原本設計用於小型資料，但對於大多數應用程式來說，仍然適合作為快取策略。 完整教學請參考我們其他關於使用鍵值儲存的資源。

  • 實作手冊（Cookbook）：將鍵值資料儲存至磁碟
  • 影片：本週套件：shared_preferences

使用檔案系統快取資料

#

如果你的 Flutter 應用程式已經超越適合 shared_preferences 的低吞吐量情境，你或許可以考慮利用裝置的檔案系統來快取資料。 更詳細的教學請參考我們其他關於檔案系統快取的資源。

  • 實作手冊（Cookbook）：讀寫檔案

使用裝置端資料庫快取資料

#

本地資料快取的終極方案，就是採用正規資料庫來讀寫資料的策略。 這類方案有多種型態，包括關聯式資料庫與非關聯式資料庫。 所有這些方法在處理大型資料集時，效能都遠勝於單純檔案存取。 更詳細的教學請參考以下資源：

  • 實作手冊（Cookbook）：使用 SQLite 儲存資料
  • SQLite 替代方案：sqlite3 套件
  • Drift（關聯式資料庫）：drift 套件
  • Hive CE（非關聯式資料庫）：hive_ce 套件
  • Remote Caching（API 回應的輕量級快取系統）：remote_caching 套件

圖片快取

#

圖片快取與一般資料快取屬於相似的問題領域，但有一套通用解決方案。 若要讓你的 Flutter 應用程式使用檔案系統儲存圖片，請使用 cached_network_image 套件。

  • 影片：本週套件：cached_network_image

狀態還原（State restoration）

#

除了應用程式資料外，你可能還希望持久化使用者會話的其他面向，例如導覽堆疊、捲動位置，甚至是填寫表單的部分進度。這種模式稱為「狀態還原（state restoration）」，而 Flutter 已內建此功能。

狀態還原的運作方式，是指示 Flutter 框架將其 Element 樹中的資料與 Flutter 引擎同步，然後由引擎將資料快取至平台專屬的儲存空間，供日後會話使用。若要在 Android 和 iOS 上啟用 Flutter 的狀態還原功能，請參考下列文件：

  • Android 文件：Android 狀態還原
  • iOS 文件：iOS 狀態還原
